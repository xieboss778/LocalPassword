# 远端布局：一桶一库，无前缀、无用户目录

## 状态

accepted（2026-11-27）

## 背景

旧布局把配置前缀、用户 id、对象类型和月份叠在同一条路径里（`<prefix>/<userId>/backups/<年-月>/<时间戳>.json`），并由「同步」与「备份」两套写路径各自维护一套对象。恢复向导只认同步写出的 `account.json`，而「立即备份」从不写它——所以只备份过的桶无法恢复。

## 决定

- 桶就是库的边界：一个桶只放一座保险库，对象直接写在桶根，不再有 prefix 与用户目录。
- `account.json` 是恢复的唯一锚点，版本升到 2，`userId` 必填；路径不再承担身份。
- 任何上传路径（同步或导出）先写 `account.json`，并校验桶的归属；写不出来或归属不符就整体失败。
- 快照写 `snapshots/<id>.json`，导出写 `exports/<年-月-日>/<id>.json`；两类历史共用一个保留数（默认 10），每次成功写入后清理，永不删清单当前指向的快照。
- 不兼容旧布局，也不探测它。

## 考虑过的方案

- **保留 prefix + 用户目录**：能支持多人共用一个桶，但路径深、恢复要在目录名里猜身份，而且两套写路径并存正是这次故障的根源。
- **兼容旧桶**：要留下定位器、前缀剥离和多账号选择，代码量翻倍；收益只是让开发期写下的旧对象可读。旧对象留在桶里，不自动删除。

## 后果

- 两个不同账号的库必须用两个桶；误配同一个桶会被归属检查拒绝，而不是静默覆盖对方的账号文件与快照。
- 恢复表单不再有「前缀」字段；用户只需端点、桶、Access Key、Secret 和主密码。
- 旧对象仍在桶里，需要时由用户在 R2 控制台手动清理。

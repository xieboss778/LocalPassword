> 日期：2026-11-27

## 0. 三条决策

1. **离线是产品定义，不是降级模式。** 同步是"可选的加密镜像"，不是主库。关掉同步，除跨端外功能零降级。
2. **1Password 的云端能力逐项做本地等价物，不做云端依赖。** 能等价的等价，不能等价的明说差异（团队权限、SSO），不用"以后上云"糊过去。
3. **多设备同步落在 Cloudflare R2（S3 兼容）上，保持可替换。** 一个桶 = 一座库；换 MinIO / S3 / Backblaze 只改 endpoint，不改代码。

### 三条不变量

| 编号 | 不变量                                                  | 验收方式                             |
| ---- | ------------------------------------------------------- | ------------------------------------ |
| I1   | 冷启动、解锁、读写、搜索、生成、填充，全部不触网        | 锁库状态抓包 + 网络闸门日志为 0 请求 |
| I2   | 同步失败不阻塞本地写入，队列持久化，重启续传            | 断网写入 100 条 → 恢复网络后自动补齐 |
| I3   | 只凭"主密码 + 桶"可重建整库，不依赖厂商、不依赖某台设备 | 空设备恢复演练（含历史、归档）       |

**明确不做**：自建服务端、账号体系、遥测、服务端合并、服务端泄露库。R2 只被当作"会 412 的硬盘"，不承担任何业务逻辑。

### 1.2 六个断点（用户视角）

1. 不会自己同步。
2. 不知道什么时候该同步（脏标记是死代码）。
3. 冲突可以看到了，也能按条目三选一（本机 / 云端 / 两份都留）。
4. 改一条 = 传全库。
5. 桶里没有"谁在写"，没有签名，没有回滚保护。
6. 失败只给一句"同步失败"。

## 2. 本地等价物清单

原则：**先问"这件事在离线时能不能成立"，再问"要不要做"。** 成立就做本地实现，不成立就明确写"不做"。

| ------------------------ | -------------- | ----------------------------------------------------------------- | ------------------------ | -------------------------------------------------------- | --------- |
| 多设备同步               | 厂商服务器     | R2/S3 端到端加密镜像                                              | 快照 + 条件写            | 引擎有，缺自动化                                         | A         |
| 条目历史 / 回滚          | 服务端存版本   | 条目内本地版本栈（≤10 版**仅存本机**，不进入 R2 快照）            | `CIPHER_VERSION_HISTORY` | 8 类条目均可查看字段级差异并一键恢复；旧版仅密文本地保存 | C         |

**必须诚实的两处**：

- **共享桶没有 per-item ACL。** 拿到桶凭证的人能读全库。所以"共享保险库"只能是家庭/小团队的**同级共享**，靠"每人一个桶 + 共享包"或"共同持有一个桶"两种模式，不承诺权限分级。
- **旅行模式在无服务端时不可能"远程移除"。** 等价物是"从不写入"+"离境前清理本机"，不是 1Password 那种"设备上消失、回来复原"。

## 3. 同步架构

### 3.1 对象布局 v2

```
account.json                      # 恢复锚点：userId / salt / KDF / wrapped user key / wrapped private key
                                  #            + 签名公钥 + vaultId（新增）
manifest.json                     # 唯一提交点：schema / generation / writer / snapshot / sha256 / sig
snapshots/<id>/index.json         # 分段索引：chunk 列表 + 每段 sha256 + 条目数
chunks/<sha256>.json              # 内容寻址分段（100 条/段，gzip）
devices/<deviceId>.json           # 设备名 / 平台 / 最后同步 / 最后 generation（新增）
attachments/<cipherId>/<fileId>   # 附件密文（可选，D 批次）
shares/<shareId>.json             # 共享包（可选，D 批次）
exports/<date>/<id>.json          # 人类可读导出（保留现状）
```

- **默认桶 = 库边界**（所有对象在根路径）；开启多保险库后，桶升为**账户边界**，每座库走 `vaults/<vaultId>/` 前缀，`account.json` 只列库 id 与加密后的库名。
- **兼容**：`schema: 2` 起算；读到 v1 的 `snapshots/<id>.json` 仍可合并，成功后按 v2 重写。至少保留一个发布周期的双读路径；prune 与 GC 需按 key 形态区分 v1 / v2，避免把 v1 快照算进 v2 的分段配额。

### 3.2 一次自动同步的时序

```
本地写 → writer 打脏标记（持久化：userId + 时间 + 次数）
      → 去抖 30s（±20% jitter）
      → 串行队列
          1. GET manifest（Class B）
          2. etag 未变且本地无脏 → 结束
          3. GET index + 缺失的 chunks（Class B）
          4. 本地合并（解密只在内存；冲突落"冲突副本"）
          5. 只重建变化的 chunk → PUT chunks（Class A）
          6. PUT index（不可变 key）
          7. PUT manifest（If-Match 旧 etag）
               412 / 429 → 回 1，最多 3 次，指数退避
          8. 成功：清脏、记 lastSyncedAt、更新 base、按需 GC
```

### 3.3 触发点

| 触发     | 时机                    | 说明                       |
| -------- | ----------------------- | -------------------------- |
| 解锁后   | 5s                      | 先拉后推，避免刚打开就覆盖 |
| 本地写后 | 30s 去抖                | 主要路径                   |
| 窗口聚焦 | 距上次 > 60s            | 切回设备即刷新             |
| 心跳     | 解锁时每 5 分钟（可关） | 接收其他设备的改动         |
| 退出前   | 尽力 flush              | 不阻塞退出                 |
| 手动     | 永远保留                | 用户始终有一键             |

**为什么不是实时**：R2 对同一 key 的**并发写限制为 1 次/秒**，manifest 是单点。实时同步会让所有设备挤在同一个 key 上互相 429。30s 去抖对密码库足够——人不会在两台设备上同时改同一条。

### 3.4 合并语义 v2

| 项         | 规则                                                                                      |
| ---------- | ----------------------------------------------------------------------------------------- |
| 版本比较   | `(lamport, deviceId)` 取代 `revisionDate`；迁移期 lamport 缺失则回退时间戳                |
| 软删除     | `deletedDate` 随记录走，UI 过滤                                                           |
| 硬删除     | tombstone，保留 90 天或被最近 N 个快照引用为止                                            |
| 冲突默认   | **保留两份**：赢家占原 id，输家写为 `conflictOf` 副本（标题追加"冲突副本 · 设备 · 日期"） |
| 用户选择   | 冲突面板逐条选"本机 / 云端 / 两份"，写入 preferences 后立即重算                           |
| 未解决冲突 | 持久化计数，设置页常驻提示，不阻塞后续同步                                                |

**为什么不继续用"时间新者胜"**：密码库里静默丢一条的代价远高于多一条副本。1Password 靠服务端串行化回避了这个问题，我们没有服务端，就只能靠"不丢"。

### 3.5 完整性与回滚保护

| 机制          | 做法                                                                       |
| ------------- | -------------------------------------------------------------------------- |
| 设备签名      | 首次配置生成 Ed25519 密钥对，私钥用 user key 包裹；公钥写进 `account.json` |
| manifest 签名 | 覆盖 `{schema, generation, snapshot, sha256, updatedAt, writer}`           |
| 回滚检测      | 每设备记 `maxGeneration`；收到更小的 generation → 拒绝并告警"云端被回滚"   |
| 分块校验      | 每个 chunk 校验 sha256，index 校验全量 hash                                |
| 提交原子性    | 只信 manifest；孤儿 chunk 由 GC 按"保留 index 的引用"标记清除              |

**边界**：能防篡改与回滚，**不能防删除**。拿到桶凭证的人仍可清空桶。缓解只有两条——本地永远保留完整副本；可选第二目标镜像（同引擎换 endpoint）。

### 3.6 体积与增量

| 指标                    | 现状（全量）                                   | v2（分段 + gzip）                             |
| ----------------------- | ---------------------------------------------- | --------------------------------------------- |
| 5000 条库的单次同步字节 | 约 5 MB                                        | 约 30–60 KB（1 段 + index）                   |
| 恢复请求数              | 2 次 GET（manifest + snapshot）                | 1 次 index + 50 次 chunk GET                  |
| Class A / 次            | 5（account + snapshot + manifest + 2 次 list） | 3（chunk + index + manifest），prune 降到每日 |
| 失败重传成本            | 全量                                           | 单段                                          |

成本不是主要矛盾：R2 免费额度为 10 GB、100 万 Class A、1000 万 Class B、出网免费；个人用户按 3 次/同步也永远用不完。**真正的收益是时间、流量、耗电和失败窗口。**

### 3.7 元数据暴露（必须写进隐私说明）

R2 能看到：条目数量、分段大小、修改时间与频率、设备数量、`account.json` 里的邮箱与 KDF 参数。

- 不做整库信封加密的原因：合并需要逐条读；全信封会让每次同步都全量解密，且失去内容寻址去重。
- 可选的缓解（P2）：gzip 后填充到 4 KB 边界；`account.json` 的邮箱改为可选或加密；桶名不含身份信息。
- 对外表述只有一句：**"R2 看不到你的密码，但能看到你在什么时候改了多少条。"**

### 3.8 恢复流程

```
输入 endpoint / bucket / 凭证
  → GET account.json（校验版本、userId）
  → 主密码派生 master key → 解 user key → 解私钥
  → GET manifest → 校验签名与 generation
  → GET index → GET chunks → 校验 hash
  → 预览"将覆盖本机 N 条 / 新增 M 条"，默认先导出本机快照
  → 写入本地 → 解锁
```

## 5. 成本与硬限制

| 项             | 数值                                                  | 对设计的影响                                          |
| -------------- | ----------------------------------------------------- | ----------------------------------------------------- |
| R2 免费额度    | 10 GB 存储、100 万 Class A、1000 万 Class B、出网免费 | 个人库远未触顶；Class A 比 Class B 贵一个数量级       |
| 同 key 并发写  | **1 次/秒**，超出返回 429                             | manifest 必须串行 + 去抖；不能做实时同步              |
| 桶管理操作     | 50 次/秒                                              | 与同步无关，配置流程注意即可                          |
| 对象大小       | 单次 PUT 5 GiB 上限                                   | 单人库不构成限制                                      |
| ListObjects    | 属 Class A                                            | prune 从"每次 push"改为"每 20 次或每天"               |
| 无对象版本控制 | —                                                     | 回滚保护只能靠签名 + generation，不能靠 S3 Versioning |
| 无多对象事务   | —                                                     | manifest 是唯一提交点；孤儿对象靠 mark-sweep GC       |

**规模测算（5000 条、gzip 后约 1.5 MB）**：保留 10 份快照约 15 MB；分段后日常同步 3 次 Class A；每天 100 次同步 = 300 次 Class A，月 9000 次，占免费额度 0.9%。

## 6. 路线图与验收

| 批次        | 范围    | 目标                          |
| ----------- | ------- | ----------------------------- |
| A（1 周）   | S1–S7   | 从"手动备份"变成"会自己同步"  |
| B（2 周）   | S8–S16  | 从"能同步"变成"敢信"          |
| C（3–4 周） | S17–S18 | 体检与旅行模式的本地等价物    |
| D           | S19–S22 | 差异化：分享、附件、多库、CLI |

> 条目历史/归档的 **UI 入口**按竞品报告批次 1 先行；S12 只补"历史与归档随同步走"的数据层，两者不冲突。

**可测验收**：

1. 锁库状态 0 网络请求；断网全流程可用；联网后队列自动补传。
2. 两台设备交替改同一条 20 次：0 静默丢失，冲突副本可解释、可合并。
3. 5000 条库改 1 条：上传 < 100 KB。
4. 把桶内 manifest 替换为旧版本：客户端拒绝并告警。
5. 空设备仅凭主密码 + 桶，10 分钟内重建全部条目（含历史、归档）。
6. 删除桶内某个 snapshot：客户端报"云端数据不完整"，不报"已同步"。

## 7. 风险与取舍（写给自己看）

| 风险         | 说明                          | 处理                                         |
| ------------ | ----------------------------- | -------------------------------------------- |
| 元数据泄漏   | 条目数、改动节奏对存储方可见  | 明说 + 可选填充；不承诺"存储方什么都看不到"  |
| 共享桶无 ACL | 有凭证即可读全库              | 只做同级共享，不做权限模型                   |
| 无推送       | 最坏 5 分钟延迟               | 聚焦触发 + 手动同步兜底                      |
| 凭证泄露     | 可写、可删、可回滚            | 签名防篡改、generation 防回滚、本地副本兜底  |
| 主密码轮换   | 其他设备的 wrapped key 会失效 | S16 专门处理，否则换密码 = 其他设备无法恢复  |
| 手动守护测试 | 现有测试把"不调度"当承诺      | 改为"锁库零请求"，承诺从"不同步"变成"不乱联" |
